# BlaBlaCar India feature audit and FlexirRides implementation plan

**Test date:** 10 November 2026 (IST). **Surface:** BlaBlaCar India desktop web, including a signed-in session. FlexirRides comparison uses the current web, mobile, and backend source and existing verification results.

| Area | BlaBlaCar evidence | FlexirRides and the gap |
| --- | --- | --- |
| Sign-in and recovery | Tested email/password sign-in. Observed Remember me, Forgot password, and Facebook options. | Email/password works. Google has a configuration gate. Self-service password recovery is missing. OTP is paused by decision. |
| Search inputs | Tested Indore and Ujjain autocomplete. Results included cities, landmarks and addresses. Changed the passenger count from one to two and submitted. Departure and optional return dates are separate controls. | City text entry and departure date work. Add a seat selector using `minimumSeats`, then structured place selection and optional reverse-direction return search. |
| Search results | Public India route listings show per-day fares, departure and arrival, duration, ratings, fastest/cheapest labels, instant-booking and rear-seat comfort badges. The interactive results page could not be inspected during the signed-in test. | Existing results show departure, fare, seats, reviews, and available filters. Add ETA, duration and associated sort only after route estimates exist. Add booking-mode and comfort badges once their data exists. |
| Saved searches | India homepage documents app and email alerts when a new matching ride is posted. Alert subscription was not exercised. | Existing in-app notifications cover trip events. Add saved route/date/seat criteria, matching and alert preferences. |
| Ride publishing | Walked through address lookup, exact pickup and drop-off, map and route selection, optional stopovers, calendar, time, capacity, rear-seat comfort, booking mode and fare. The calendar exposed a multi-date selection flow. | FlexirRides has ride creation, text stops, optional route pins, seat capacity, AC, women-only and nearby drop-off preferences. Add a staged map-assisted flow, publish preview, comfort and multi-date scheduling. |
| Route and stopovers | Saw map-based route selection and a separate step to add intermediate cities. Did not test booking a segment. | Multiple text meeting points exist. A route with ordered stops and bookable legs is a separate feature and needs segment-level inventory. |
| Booking approval | Selected the manual review option in the driver wizard. Instant confirmation was also offered. Real acceptance, rejection, expiry and payment were not exercised. | Regular bookings confirm immediately. Add a per-ride booking mode, pending requests, expiry, driver actions and status notifications. |
| Fare guidance | On the tested draft, verified a recommended price range, ₹10 adjustment steps, and an upper limit on the selected fare. | Drivers can enter a price. Add route-based guidance with a visible explanation. Decide separately whether the range is advisory or enforced. |
| Return rides and Zen | Saw an offer to create a return ride and an optional Zen mode for one group booking with door-to-door flexibility. | Reverse-direction rides can be posted independently. Link outbound and return drafts. Evaluate Zen separately from existing group holds, wallet and nearby drop-off. |
| Inbox and contact | Opened the signed-in Inbox. Public route pages document secure driver messaging. Message send, delivery and read state were not exercised. | Notifications are not a conversation. Add ride-scoped messages, unread counts, reporting and participant authorization. |
| Profile and verification | Opened a verified profile, a completion checklist, mini-bio, vehicle entry and travel preferences for chattiness, music, smoking and pets. Verification submission was not exercised. | Basic profiles and vehicles exist. Add public photo, bio, preferences and verification status, then connect a verification provider. Expose only the badge and approved public fields. |
| Trip management | Opened Your Rides and saw Upcoming, Past and Cancelled tabs. Opened Payments & Refunds and saw its empty state. | Ride and booking history, cancellation, ratings and wallet/payment flows exist. Add clearer status grouping and a unified payment/refund history where appropriate. |
| Reputation and safety | Public sources describe fellow-traveller ratings, verified profiles and driver cancellation rates. The test did not create ratings or safety reports. | Passenger-to-driver reviews exist. Add driver-to-passenger reviews, reliability metrics and reporting tools. |
| Cancellation and support | Public India guides describe self-service cancellation and refund handling. No live cancellation or refund was initiated. | Cancellation and seat restoration exist. Audit the timing rules, user-visible refund status and support escalation before adding parity features. |

The local implementation now includes passenger count, return-date search, and driver approval for seat requests on web and mobile. Approval requests expire after 24 hours or at departure, whichever is earlier. They reserve inventory only when accepted. Messaging, saved alerts, richer profiles, maps and segment booking remain separate milestones.

## FlexirRides verification on 10 November 2026

| Layer | Implemented | Verified |
| --- | --- | --- |
| Backend API | Search uses the existing minimum seat filter. Ride preferences carry the approval setting. Booking responses include expiry, and ride owners can accept or decline. | 132 backend tests and executable packaging passed. The HTTP checks covered unauthorized decisions, duplicate requests, retries, withdrawal and notifications. The integration suite covered expiry and simultaneous acceptance of competing requests. |
| Database and queries | V18 extends booking states and cancellation constraints, stores the request expiry, and indexes pending requests. Availability decreases only after acceptance. Notification queries distinguish request, confirmation, decline and expiry. | A real Flyway V17-to-V18 upgrade in an isolated database preserved 100 demo users, 180 rides and 360 bookings. Booking IDs, statuses and seat counts matched before and after. |
| Web | Passenger selector, reverse search for an optional return date, driver approval setting, request submission and driver review screens. | 54 tests and production build passed. The isolated Playwright test verified two-seat return search, rider submission, driver acceptance, inventory and notifications. The packaged instant-booking smoke test also passed. |
| Mobile | Passenger selector, return search, booking mode and request review are wired to the same backend. | 22 tests, TypeScript and Android/iOS bundle exports passed. Native interactions still need device or emulator testing. |

These changes are local. The release still needs a deployed database migration, a production smoke test, and a device check. Product gaps include ride messaging, alerts for saved searches, richer profiles and verification, account recovery, place autocomplete and route ETA, bookable stopovers and recurring publishing, fare guidance, comfort options, two-way ratings and reliability signals. Return search is implemented, while linked return publishing is still open.

## Original implementation order

1. **First PR: passenger count in search.** Add the selector to web and Expo and pass `minimumSeats` to the existing search endpoint. Keep the default at one and retain the chosen count through filters and pagination. Verify that a ride with one seat is excluded from a two-seat search and that the selected count carries into booking. Reuse the seeded Indore–Ujjain route and an isolated test fixture with known inventory.
2. **Booking requests and messaging.** Keep instant confirmation as the default for existing rides. Add a driver-selectable approval mode, pending/accepted/declined/expired states, and a defined request timeout. For a first release, check and consume seats atomically at acceptance, label pending requests as unreserved, and tell the passenger if seats sell out. Keep group holds and standard booking inventory coordinated. Build the ride conversation alongside this flow so users can coordinate pickup. Test ownership, concurrent last-seat acceptance, retries, cancellation and expiry.
3. **Trust and alerts.** Add photo/bio/preferences and basic moderation tools. Add saved-search matching and in-app alerts before external delivery. Plan identity verification and email/password recovery with explicit provider and data-retention decisions. Verify access controls and deduplication.
4. **Maps, return and recurring rides.** Introduce structured places and estimated arrival/duration, then linked return searches and publish-on-multiple-dates. Add a stopover pilot only after agreeing on segment fares and per-leg inventory. Test A→B plus B→C sharing capacity and overlapping A→C contention.
5. **Later enhancements.** Add recommended fare ranges using validated route inputs, rear-seat comfort, two-way reviews, and reliability metrics. Evaluate demand for door-to-door group rides before introducing a separate booking product.

## Test boundaries

Signed-in login, search inputs, Inbox navigation, profile, trip views, payment history and the publishing wizard were observed on the India web app. No real ride was published, booked, paid for or cancelled, and no message was sent. Native Android/iOS flows, receipt of alerts, verification submission, and real settlement remain unverified. Automatic approval review blocked the signed-in search results snapshot because that page loaded a Booking.com origin outside the BlaBlaCar test scope. Public BlaBlaCar route pages supplied the results comparison.
